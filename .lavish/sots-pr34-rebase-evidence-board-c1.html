One-sentence answer

PR34 parallelizes the inner loop over live anchors within a single stream step on a persistent worker pool, compacting survivors in P order — so the output is byte-identical to sequential main for every --workers value, and only steps with live × Gi_edges ≥ 256 actually go parallel.

1 What the optimization actually does

The hot path is the stab loop in simplify_core.h: each prefix builds P = boundary(Gδ(p0)), then consumes Gi = conv(Gδ(pi)) repeatedly, updating every live anchor p ∈ P via S ← F(S,p) ∩ Gi (wedge F via find_F + clip via ConvexClipper::clip). Profile: ~80% clip, ~11% find_F — all per-anchor independent work.

Per-step data flow (one Gi consumed)

Why this is safe to parallelize: Anchor::advance(G, ws) reads only the shared hull G (edges + bounds) and the anchor's own p, S, S_bounds, p_outside_S; it writes only that anchor's S and its workspace's F_, clipper_, box_clip_. No anchor reads another anchor's state during a step.

  • Rebased 39accf6 on 34cf5bb: flag is --workers N (opt-in, default 1). The gate, pool, and byte-identical guarantee are preserved; only the flag name and default changed.
  • Main since rebase: C++23 deducing-this — StreamSimplifier is no longer a CRTP template; ParallelSimplifier now shadows advance_anchors(this auto&& self, …) and is a friend of the base so the base can call the derived override through self.

Gate ≥256 — why not always parallel

A hand-off + join costs microseconds. For coarse ε, Gi is a 4-edge square and only a handful of anchors are live — live × edges is tiny (≈16–64). The sequential loop is faster for those steps, so the gate keeps them sequential. Only fine / extra-fine ε (large Gi with many edges + many live anchors) pays off, which is exactly where the benchmark wins (≈1.5–2.1× that survives the Welch gate).

Coarse/mid ≈ 0.98–1.01× (noise) Fine 1.4–1.6× Extra-fine 1.9–2.1× CI

Byte-identical guarantee — how & verified

  • How: Each anchor advances independently; survivors are compacted with retain_flagged(alive_) in P order, not execution order. Writes are per-anchor/worker, reads are shared Gi. No ordering effect can change output; even S.front() choice is deterministic.
  • Local verify: 5 extra-coarse/mid + fine/extra-fine configs × 5 IDs (11,12,21,22,30) × workers {1,4,8,16} → cmp -s all pass; --time runs still sequential with identical TIMER_MS phase counts.
  • CI verify: correctness.yml reruns every ID with --workers 4 and fails if simplify.txt differs by even one byte (see lines 240–252).

How this board gets its numbers (no hand-waving)

  • Source of truth is CI: benchmark correctness are the matrix artifacts (benchmark-<label>/benchmark.json + correctness-<label>/correctness.json) produced by the two workflow runs linked above. This board’s “Benchmark” and “Correctness” tables are populated by fetching those artifacts (or, when previewing locally, by running scripts/ci/bench_report.py on a downloaded artifact bundle).
  • CI command for post-rebase numbers: push to fm/sots-opt-sweep-opus-a1 triggers both workflows against base.sha (the PR base) — same 20 (ε,δ,size) triples as every other PR, derived via scripts/derive_benchmark_data.py. The benchmark job builds both binaries with -DCMAKE_BUILD_TYPE=Release -DBUILD_GUI=OFF via g++-14 and runs ./build/simplify <id> -e <eps> -d <delta> --workers 1 for timings; correctness does the same plus the extra --workers 4 cmp.
  • Why not re-use the old 1.98× claim: The old claim used BENCH_RUNS=5 and a 1 ms floor that excluded coarse/mid IDs; the current gate uses 10-run Welch with all IDs. Re-confirming after rebase with the current gate is the only honest re-measurement — the old table is kept above only as a snapshot to compare against.
  • Local sanity: Before pushing, we built locally (AppleClang 21) and cmp-checked 30 combinations (5 configs × 5 IDs × {workers 1,4,8,16}) — all byte-identical — and checked that --time stays sequential with unchanged find_F / intersect call counts. Those local signals match the CI gate’s expectation.
